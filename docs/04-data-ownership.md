# Part 9 — System of Record Matrix

| Fact | Canonical system | Projection and writers | Direction and conflict handling | Reconciliation |
|---|---|---|---|---|
| Account/person identity | PostgreSQL | CRM identity fields; identity command is only canonical writer | DB→CRM; CRM correction creates conflict task, never silent overwrite | Daily IDs/field hashes plus webhook hints |
| Employment/contact method | PostgreSQL with source evidence | CRM selected fields; research service proposes | New vendor observation→reviewed DB update→CRM | Revalidate before use; stale employer blocks person-level claims |
| Evidence, signals, scores | PostgreSQL | Console/context packs | Append revisions; deterministic scores; retraction invalidates derived outputs | Expiry sweep daily and every dispatch |
| Operational Lead stage | PostgreSQL | Console, selected CRM labels | Prospecting commands only; qualified≠CRM won | Event replay and daily invariant scan |
| Deal stage, amount, owner, next step | Pipedrive | Read-only DB Opportunity | Console submits CRM command; projection changes only after provider read/receipt. External CRM changes remain observed truth but can be flagged policy-invalid | Webhook fetch plus 5-min delta and daily full reconciliation |
| Message draft/version | PostgreSQL metadata + Drive bytes | Sequencer deployment | Approved render→provider; provider copy drift invalidates execution | Before release and periodically while active |
| Campaign intended scope | PostgreSQL CampaignVersion | Provider config | Local approved version→provider; unapproved provider edits cause pause | Config hash comparison |
| Campaign/enrolment execution | Smartlead | Local observed projection | Provider events/reads→DB; local desired state is separately labelled | Active 60-s safety poll; periodic full counts/history |
| Send/acceptance/bounce/reply | Mail/sequencer provider | Interactions/message references | Append observed facts; old events cannot reverse suppression or final send receipt | Event IDs/history replay with overlap |
| Suppression/eligibility | PostgreSQL authoritative policy plus mandatory provider enforcement | Sequencer stop state | Any trusted opt-out→local deny→provider stop; deny wins conflict | Highest-priority propagation and continuous divergence checks |
| Meeting schedule/cancellation | Google Calendar | Meeting projection | Calendar→DB; V1 founder books in existing Calendar UI | Push hints plus sync token and 5-min catchup |
| Attendance/qualification | Human-confirmed operational record and CRM commercial acceptance respectively | Meeting outcome and CRM stage | No attendance inferred from elapsed time; material CRM transition requires founder command | Weekly exceptions |
| File bytes and editable documents | Google Drive | Metadata, hashes and derived search chunks | Drive→catalogue; generated bytes uploaded through adapter; approval freezes independent export | Change token, ACL checks, daily completeness |
| Final signed contract | Approved signing system/archived final Drive copy | Contract metadata | Human attestation to exact signed version | Hash and signature evidence validation |
| Policies/approvals/workflow | PostgreSQL plus versioned policy source | Console/n8n telemetry | Command service only; n8n callbacks cannot mutate status arbitrarily | Invariant scans/outbox receipts |
| AI result | PostgreSQL validated proposal + document artifact | Domain state only after separate validation/command | Model→proposal→validator→permitted commit | Evaluation and provenance checks |
| Client engagement/deliverables | PostgreSQL | CRM links/reports | Scope/acceptance commands with contract authority | Due-date and acceptance evidence checks |
| Invoice, cash, recognised revenue | Future ledger/bank; outside V1 write scope | Reviewed financial snapshots | Import only; missing source means unavailable | Human source reconciliation |

CRM stage validation is enforced for Company OS commands. If a human changes a Pipedrive stage directly, the projection must reflect it and create an exception when evidence is missing; the system cannot honestly claim to prevent all native CRM edits without verified provider restrictions. Downstream onboarding remains blocked until its own evidence gates pass.
