# Part 24 — Environments and Deployment

| Environment | Database/data | Credentials and AI | Sending/webhooks | Purpose and gate |
|---|---|---|---|---|
| Local development | Local PostgreSQL, synthetic fixtures, isolated Auth dev project or managed test identity | Fake providers by default; optional explicitly budgeted development AI key | Fake sequencer only; local webhook fixtures | Fast iteration; no production data or keys |
| Automated test | Ephemeral PostgreSQL with same major version and migrations as target | Deterministic fakes; no network for ordinary CI | Adversarial fixture events | RLS/constraints/concurrency/contracts |
| Staging | Separate managed database/Auth project and Drive folders/calendar | Separate provider accounts/test credentials and capped AI keys | Hard recipient allowlist of founder-owned test mailboxes; server egress and adapter guards; distinct webhook domain | Account preflight, E2E, fault injection, five-day shadow period |
| Production | Paid managed PostgreSQL and approved workspaces | Production service credentials from secret store; routes enabled only after gates | Sending disabled until phase release decision; provider callback endpoints always authenticated | Governed live operations with backups, monitor and human owner |

**OPS-020 Initial deployment choice.** One paid Render web service for Next.js, one paid Render web service for FastAPI and one paid background worker using the same Python package/release. Supabase PostgreSQL and Auth are managed dependencies. n8n Cloud is optional integration plumbing and may be provisioned only when a proven connector task needs it. No Redis, Kubernetes or separate vector service is required for V1. Docker MAY provide reproducible dev/CI packaging; do not force the founder to maintain a VPS.

Render background workers run continuously and cannot receive inbound traffic, so callbacks go to FastAPI. HTTP health probes are available for web/private services; worker health is our heartbeat plus independent monitoring. Environment secrets are supported. [Render background workers](https://render.com/docs/background-workers), [Render health checks](https://render.com/docs/health-checks), [Render secrets](https://render.com/docs/configure-environment-variables). Select paid always-on service types after a current cost quote; no assumption that free services or a single quoted hosting fee cover all three processes.

Choose database/application regions close enough to keep measured transaction latency acceptable, subject to client/provider data policy. Do not choose a region merely by founder location. Record region and processing restrictions in the connection report. Use TLS for browser/API/database traffic, a private API-to-worker/DB path where supported, restricted CORS and payload limits. `/health/live` proves process alive; `/health/ready` checks essential DB connectivity and schema compatibility without leaking details. Vendor outage does not necessarily make API unready; it disables affected operations and appears in health.

Deploy immutable commit builds after review. Apply backward-compatible expand migrations through a separate release identity; deploy API/worker that tolerate current and next schema during rollout; validate then contract in a later release. Never migrate on every web process boot. Background worker drains on termination: stop claims, finish bounded local transactions, mark uncertain external effects when receipt is not known, allow leases to expire. Overlapping old/new workers are expected and tested with fencing/effect keys. Roll back code only when schema remains compatible; irreversible data changes require forward fix or tested restore.

**OPS-021 Backups.** Before live client dependency, verify ≤4-hour operational capture or PITR and a restore drill; daily-only backup is not enough for that target. Supabase documents PITR as the route for a lower RPO. [Supabase production checklist](https://supabase.com/docs/guides/deployment/going-into-prod). Backup database, restricted document snapshots, current provider exports where permitted, workflow definitions, schemas, policies and deployment configuration; keep credential recovery separate. Erasure/suppression ledger must be captured more durably than the state it protects and reapplied before restoring access. Test encrypted backup access by an authorised recovery operator. If budget cannot support the required operational recovery, stay in research/preparation mode until the founder approves a revised scope or recovery policy.

No cost amount in the source report is treated as a current procurement quote. Phase 2 can run with local fakes. Before paid staging/production, present itemised current monthly and variable estimates, maximum exposure, recovery cost and cancellation terms. Founder approves the budget once; technical implementation then uses that envelope without repeated permission for routine reversible work.
